# v5 React 16.8, SSR and Identity Contract

v5 retains `peerDependencies.react >=16.8`.

That decision has runtime consequences and is verified with real old-React consumers, not only source scanning.

## 1. Runtime API floor

While the peer floor remains 16.8, runtime implementation MUST NOT depend on:
- `useId`;
- `useSyncExternalStore`;
- `useInsertionEffect`;
- `useTransition`;
- `useDeferredValue`;
- React 18 root APIs.

The existing static React-floor scan remains useful but is not sufficient by itself.

## 2. Real compatibility fixtures

CI MUST build the packed v5 artifact and execute a minimal consumer against:
- React 16.8.x + matching ReactDOM;
- the repository's current React version.

The React 16 fixture must verify:
- default picker mount/unmount;
- primitive Root/Panel/Search/Viewport/List mount;
- click selection;
- keyboard search/navigation smoke path;
- SSR render using `react-dom/server`;
- hydration using the React-16-supported hydration API;
- no runtime missing-hook errors.

Type declarations are compiled against a compatible `@types/react` fixture where practical.

## 3. Initial v5 generates no library-owned DOM IDs

v5 MUST remove the current fixed document-global IDs:
- `epr-search-id`;
- `epr-category-nav-id`.

Initial v5 does **not** add an `idPrefix` API.

Instead, the initial implementation must avoid library-owned ID/IDREF relationships entirely where they are unnecessary:

- the polite search-status live region does not require the input to point to it with `aria-controls`;
- category tabs must not point to the tablist itself;
- category/grid navigation uses Root-scoped refs/registry rather than document IDs;
- internal ownership/registration uses opaque JavaScript identities, not DOM IDs.

A consumer-supplied native `id` on a primitive remains allowed and consumer-owned.

If a future feature truly requires a generated DOM ID/IDREF relationship, that feature must separately design:
- deterministic SSR identity;
- multiple-root collision behavior;
- any public prefix/ID escape hatch actually required.

Do not reserve public API for a hypothetical requirement.

## 4. Internal subscriptions

Because `useSyncExternalStore` is unavailable, v5 should prefer:
- stable service objects in context;
- narrowly split state contexts;
- refs for imperative/high-frequency state;
- React 16.8 `useState`/`useEffect` only where subscription is needed.

Do not recreate an omnibus frequently changing context merely to avoid a React-18 API.

## 5. Hydration

The first client render must structurally match SSR output.

Specifically:
- no localStorage-derived suggestions before hydration completes;
- no client-only generated IDs in first-render markup;
- no viewport measurements that change required server markup before effects;
- controlled search initial markup derives only from props;
- native/document queries begin after mount.

Hydration tests run with multiple picker Roots in the same document.

## 6. Accessibility identity tests

In fixtures that do not provide consumer IDs, acceptance must assert:
- one default picker contains zero `[id]` attributes generated by the library;
- two default pickers still contain zero library-generated IDs;
- one primitive composition contains zero library-generated IDs;
- two primitive Roots contain zero library-generated IDs;
- no library-generated `aria-controls`, `aria-labelledby`, or `aria-describedby` IDREF is emitted.

If future v5 implementation discovers an unavoidable IDREF requirement, that is a contract change and must be resolved before merge rather than silently adding a global counter.
