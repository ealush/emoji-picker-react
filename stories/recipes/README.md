# Recipes and design examples

25 copy-paste starting points that show emoji-picker-react fitting into real
products — chat composers, comment threads, reaction bars, status dialogs,
mobile sheets, icon pickers — each implemented in **seven styling stacks**:
plain CSS, CSS Modules, Emotion, styled-components, MUI, Tailwind v4 and
shadcn/ui. All seven render pixel-identically.

Each folder is self-contained:

| File | What it is |
| :-- | :-- |
| `shell.tsx` | The composition (which parts, in what arrangement) plus mock app chrome |
| `picker.css` | The picker's styles — the source of truth for every stack |
| `app.css` | Styles for the mock app around the picker (not needed when copying) |
| `recipe.json` | Title, export name, root class and root component |
| `picker.module.css`, `<Name>.stories.tsx` | Generated by `npm run recipes` — do not edit |

To reuse one: copy `shell.tsx` (drop the mock chrome) and `picker.css`, or
the generated stack variant matching your project from `<Name>.stories.tsx`.

All recipes follow the same rules:

- colors and sizes come from `--epr-*` tokens or plain CSS on the stable
  `[data-epr-part]` hooks; library tokens are declared at zero specificity,
  so ordinary CSS overrides them without specificity tricks (the Tailwind
  and shadcn/ui variants pass `cssLayer="epr"`);
- structural properties (viewport overflow, list/category layout, emoji cell
  geometry) are never overridden;
- behavior — keyboard navigation, focus, virtualization, variations,
  accessibility — is untouched, whatever the markup.

Coverage comes from two Playwright suites (discovered by the `recipe` tag,
so new folders are picked up automatically):

- `playwright/recipes.spec.ts` — one `<recipe>.png` baseline per recipe,
  established by the plain-CSS story. Every other stack (CSS Modules,
  Emotion, styled-components, MUI, Tailwind, shadcn/ui) is compared
  against that same file, so a stack that renders differently fails. Each
  story also gets axe (WCAG 2.1 AA) and keyboard checks.
- `playwright/recipes-interactions.spec.ts` — each recipe's plain-CSS
  story walked through every interaction state it supports (`--hover`,
  `--keyboard-focus`, `--search-results`, `--empty-search`,
  `--category-navigation`, `--skin-tone-open`, `--variations-open`,
  `--reactions-expanded`), with a functional assertion plus a screenshot
  per state. States a recipe does not have (no search box, no skin tone
  fan, no variations, non-expandable reactions) are skipped.

To add a design: copy a folder, edit `picker.css` / `shell.tsx`, run
`npm run recipes` to regenerate the seven stacks, then run the two suites
with `--update-snapshots` and look at every new image before committing.

## Composition and acceptance gates

Primitive recipes express control presence and placement through JSX. Use
`<Search><SkinTone /></Search>` for an attached tone control, or put `SkinTone`
in a consumer row. Omit it for designs without that control; do not pass the
default picker's placement/visibility switches to `Root`.

`npm run check:contracts` compiles the actual recipe shells and registry source.
Injected styling wrappers retain the appropriate `RootProps` or default-picker
prop contract, so removed props fail checking instead of being silently ignored.

CI also runs `playwright/adoption-behavior.spec.ts`: caret insertion, dismissal
and focus restoration, registry controls, nested Escape, shadow DOM, RTL,
columns and reduced motion. Arrow traversal follows composed region DOM order.
